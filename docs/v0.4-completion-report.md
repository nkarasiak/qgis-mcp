## Deviations from DESIGN.md

1. **Headless implementation reuses the plugin class instead of a parallel
   handler set.** DESIGN.md §2 says "the executor abstraction hides the
   difference" but doesn't prescribe how. We pick re-use over duplication:
   `headless_runner.py` instantiates `QgisMCPServer(host="", port=0, iface=_StubIface())`
   and dispatches through `execute_command`. The stub `iface` no-ops UI calls
   the v0.3+v0.5 surface doesn't need; handlers that genuinely need a canvas
   (`get_canvas_extent`, etc.) raise loudly. Trade-off documented in
   DESIGN.md §8 #14.

2. **Linux/macOS launcher detection is naive.** DESIGN.md §4 mentions
   `qgis_process` / standalone PyQGIS as the headless target. v0.4 only
   auto-detects on Windows (OSGeo4W locations). On non-Windows the executor
   falls back to `sys.executable` and assumes PyQGIS is importable from it.
   Users on Linux who installed QGIS via apt/conda usually have this; if a
   user reports a missing `qgis` import, we'll need to add a more explicit
   probe. Tracking: DESIGN.md §8 #15.

3. **`qgis_eval` still stubbed.** v0.5 work; not a v0.4 regression.

## Notable issues found

- The QGIS LTR Python (OSGeo4W) does not have `qgis_mcp_north` installed in
  its site-packages, so `python -m qgis_mcp_north.executors.headless_runner`
  fails with `ModuleNotFoundError`. **Fix:** invoke the runner by absolute
  script path (`headless_runner.py`), and have the runner bootstrap its own
  `sys.path` to import `qgis_mcp_north_plugin`. This avoids any dependency
  on the QGIS Python's site-packages and means the user doesn't need to
  `pip install` anything into the QGIS environment.
- A pre-existing `RUF043` lint finding in `tests/test_figures_to_pptx.py`
  (regex-metacharacter not escaped) was fixed during v0.4 — the v0.3 report
  claimed "0 lint findings" because newer ruff added that rule.

## Proposed scope for v0.5

Ship the remaining 8 workflow tools, in order of complexity:

1. **`qgis_eval`** — thin wrapper over the plugin's existing `execute_code`
   handler. Adds the `return_vars` capture path (run code, then evaluate
   each var name in the local scope, JSON-serialize). 30 minutes.
2. **`qgis_export_layout`** — wraps plugin's `export_layout`. Open `.qgz` →
   find layout by name → export. ~1 hour.
3. **`qgis_project_load`** — wraps plugin's `load_project` + new
   `list_layouts` round-trip + `get_layers` for the response shape. ~1 hour.
4. **`qgis_style_categorized` / `qgis_style_graduated`** — wrap plugin's
   `set_layer_style` (which already handles all three modes). MCP-side
   work is just shaping the params and translating the response. ~2 hours.
5. **`qgis_batch_render`** — fan-out: open template, iterate values, filter
   active layer, render via `render_layers_to_path`. Manifest in response.
   ~3 hours; needs careful error handling per iteration.
6. **`qgis_render_trajectory`** — read CSV (stdlib `csv`), build memory
   layer with point geometries, optionally use `movingpandas` if available.
   `sample_rate` + `max_points` enforcement. ~4 hours; the big-data
   discipline path is the work.
7. **`qgis_render_od_flows`** — read OD CSV, look up zone centroids,
   build memory layer of arc geometries, render. ~4 hours.

Total v0.5: ~16 hours. The first three are mechanical wiring and could
land in one session each. The rendering tools (5–7) are each their own
plan, with their own end-to-end test against real PFLOW data.

After v0.5, v1.0 is just verification: run a single LLM prompt that
chains `qgis_layer_inspect` → `qgis_render_choropleth` → `qgis_render_od_flows`
→ `qgis_figures_to_pptx` against W17-style data and confirm the deck opens.
